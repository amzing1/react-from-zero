## 1. 核心概念（35 min）

### 1.1 useReducer API

```tsx
const [state, dispatch] = useReducer(reducer, initialState)

function reducer(state: State, action: Action): State {
  // 返回新状态；纯函数
}

dispatch({ type: 'ADD', title: '学习 React' })
```

- `reducer(state, action) => newState`
- `dispatch(action)` 触发 reducer；多次 dispatch 会被批处理，按顺序执行
- dispatch 的引用是稳定的，可以安全地放进依赖数组（020）
- 惰性初始化：`useReducer(reducer, initialArg, init)`，`init(initialArg)` 返回初始状态

### 1.2 reducer 必须是纯函数

- 不改 state、不发请求、不读写 DOM/localStorage
- 相同 `(state, action)` 必须返回相同结果
- 返回新对象/新数组：`{ ...state }`、`state.map`、`filter`
- 返回同一个引用（`Object.is` 相等）时，React 会 bailout
- 开发 StrictMode 会**双调用 reducer** 来检查纯度

### 1.3 action 与 TypeScript 判别联合

```ts
type Action =
  | { type: 'ADD'; title: string }
  | { type: 'REMOVE'; id: string }
  | { type: 'ADVANCE'; id: string }
  | { type: 'RESET' }
```

```ts
function reducer(state: Task[], action: Action): Task[] {
  switch (action.type) {
    case 'ADD':
      return [...state, { id: crypto.randomUUID(), title: action.title, status: 'todo' }]
    case 'REMOVE':
      return state.filter((t) => t.id !== action.id)
    case 'ADVANCE':
      return state.map((t) =>
        t.id === action.id ? { ...t, status: nextStatus(t.status) } : t,
      )
    case 'RESET':
      return []
  }
}
```

- 判别联合让 `switch` 自动收窄 `action` 类型；漏写 case 时用 `never` 做穷尽检查
- action 是“发生了什么”，不是“怎么改”；reducer 决定怎么改

### 1.4 什么时候用 useReducer

| 场景 | useState | useReducer |
|---|---|---|
| 简单独立值（开关、输入） | ✅ | 过度设计 |
| 多个子值一起变 | 多个 setState 难同步 | ✅ |
| 下一个状态依赖上一个，逻辑复杂 | 容易写错 | ✅ |
| 多个事件处理同一份状态 | 回调散落 | ✅ 统一 dispatch |
| 需要把状态逻辑抽出来测试 | 难 | ✅ reducer 是纯函数 |
| 状态机 / 有限状态 | 布尔组合爆炸 | ✅ |

**判断口诀**：状态变化逻辑开始“绕”、或者多个 setState 需要同步时，换 reducer。

### 1.5 状态机思维：消灭不可能状态

```ts
// ❌ 布尔组合：可能同时 isLoading 和 isError
{ isLoading: boolean; isError: boolean; data?: string; error?: string }

// ✅ 判别联合：任意时刻只有一个 status
type FetchState =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; data: string }
  | { status: 'error'; message: string }
```

- 状态是有限的、互斥的；事件（action）驱动状态转移
- 用 `switch (state.status)` 渲染，TypeScript 保证每个分支的数据可用
- 非法转移（如 loading 时再次 FETCH_START）可以在 reducer 里忽略或抛错

### 1.6 Vue 对照

| Vue | React |
|---|---|
| Pinia action 直接改 state | reducer 返回新 state |
| Vuex mutation / action | reducer + dispatch |
| `reactive` 多个字段 | 判别联合 + 状态机 |
| 组件内逻辑 | reducer 可抽到模块层测试 |
| 异步 action | reducer 必须同步纯函数；异步放事件/Effect |

### 1.7 常见坑

1. reducer 里 `state.push` / 直接改对象 → 不更新或状态错乱
2. reducer 里发请求/写 localStorage → 不纯
3. render 期间 dispatch → 无限循环
4. 简单开关也上 reducer → 过度设计
5. action type 拼写错误 → 用 TS 联合类型 + 穷尽检查
6. 把派生值放进 state → 继续用 render 派生

### 我的实现 / 遇到的问题

**TaskReducerDemo**

- `Task { id, title, status }`；Action 判别联合 `ADD / REMOVE / ADVANCE / RESET`
- id 在事件处理函数生成、随 action 传入（reducer 内 `crypto.randomUUID()` 不纯，StrictMode 双调用会生成两个 id）
- 空输入：按钮 `disabled` + 提交前 `trim()`；草稿值用 `useState`，任务列表用 `useReducer`
- `next(status)` 穷尽三态；`done` 终止，前进按钮禁用
- 三个状态数量在 render 时用 `filter` 派生
- 穷尽检查：`default` 里 `const _exhaustive: never = action`

**StatusMachineDemo**

- `FetchState` 判别联合：idle / loading / success(data) / error(message)
- 非法转移守卫：loading 时拒绝 `FETCH_START`；非 loading 时拒绝 SUCCESS/ERROR
- loading 时禁用两个发起按钮，避免两个定时器赛跑
- 已知限制：reset 后立刻重新发起，旧定时器可能在新一轮 loading 中落地；真正的请求竞态用请求标识/取消解决（Day 020）

**踩坑**

- 初版在 reducer 内生成 UUID → 不纯；改为 action 携带 id
- 初版 `default: throw` 没有编译期穷尽检查 → 改为 `never`
- 两个模拟 success/error 的按钮连点，先到的定时器生效 → loading 时禁用按钮
- `default` 分支裸写 `const` → 加花括号（no-case-declarations）

## 4. 总结与复习卡（10 min）

### 今日一句话总结

useReducer 把"发生了什么（action）→ 状态怎么变（reducer）"集中管理；判别联合 + 状态机让不可能状态在类型层面无法构造；reducer 必须纯，因为 React 会多次调用它（StrictMode 双调用会放大副作用）。
