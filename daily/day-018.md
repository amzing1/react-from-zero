### 1.2 状态分区（本课重点）

每个状态先回答三个问题：

1. **谁拥有它？** 谁能最近地读写它；能放局部就不上升
2. **它是数据还是 UI？** 领域数据 vs 界面控制
3. **它能不能派生？** 能算出来的不要存

| 状态 | 示例 | 放哪 | 理由 |
|---|---|---|---|
| 任务集合 | `tasks` | `TaskProvider`（reducer + Context） | 跨组件共享、多个事件修改、需要统一动作 |
| 筛选条件 | `keyword / status / priority` | `TaskBoard` 本地 `useState` | 只有面板自己用；离开页面即重置；后续可进 URL |
| 表单草稿 | 新增/编辑中的字段 | 表单组件本地 state | 提交前不共享；编辑要能取消回滚 |
| 派生值 | 过滤结果、计数、空状态 | render 时计算 | 存 state 会与源数据不同步 |

反例：把 `filteredTasks` 存进 state，删除任务后忘记同步 → 列表与计数打架。

### 1.3 数据模型

```ts
export type TaskStatus = 'todo' | 'doing' | 'done'
export type TaskPriority = 'low' | 'medium' | 'high'

export interface Task {
  id: string
  title: string
  description: string
  status: TaskStatus
  priority: TaskPriority
  dueDate: string | null // 'YYYY-MM-DD'
  createdAt: string      // ISO，事件处理里生成
}

export interface TaskFilter {
  keyword: string
  status: TaskStatus | 'all'
  priority: TaskPriority | 'all'
}
```

要点：

- `id` / `createdAt` 在**事件处理函数**里生成，随 action 传入；reducer 内生成违反纯度（016 踩坑）
- `status`/`priority` 用字符串联合，不用 `enum`（TS 工程基线：`erasableSyntaxOnly`）
- `dueDate` 可空，筛选/排序要处理 `null`

### 1.4 Action 设计

两种风格，选一种并说清理由：

```ts
// A. 显式动作（可追踪、类型收窄细）
type TaskAction =
  | { type: 'task/created'; task: Task }
  | { type: 'task/titleChanged'; id: string; title: string }
  | { type: 'task/priorityChanged'; id: string; priority: TaskPriority }
  | { type: 'task/statusChanged'; id: string; status: TaskStatus }
  | { type: 'task/deleted'; id: string }

// B. 泛化 patch（动作少，但类型要限制可改字段）
type TaskPatch = Partial<Pick<Task, 'title' | 'description' | 'priority' | 'status' | 'dueDate'>>
type TaskAction =
  | { type: 'task/created'; task: Task }
  | { type: 'task/updated'; id: string; patch: TaskPatch }
  | { type: 'task/deleted'; id: string }
```

- 状态流转（todo→doing→done）可以作为单独 action `task/statusAdvanced`，让 reducer 决定下一状态
- 不改任务时返回原数组 / 原对象引用，React 才能 bailout
- `switch` 用 `never` 做穷尽检查

### 1.5 Context 结构

```tsx
// task-context.ts —— 纯 TS，避免 Fast Refresh only-export-components 警告（017 遗留）
export const TaskStateContext = createContext<Task[] | null>(null)
export const TaskDispatchContext = createContext<Dispatch<TaskAction> | null>(null)

export function useTasks(): Task[] { /* null 检查并抛错 */ }
export function useTaskDispatch(): Dispatch<TaskAction> { /* 同上 */ }
```

```tsx
// TaskProvider.tsx
export function TaskProvider({ children }: { children: ReactNode }) {
  const [tasks, dispatch] = useReducer(taskReducer, seedTasks)
  return (
    <TaskStateContext value={tasks}>
      <TaskDispatchContext value={dispatch}>{children}</TaskDispatchContext>
    </TaskStateContext>
  )
}
```

- `tasks` 只在 reducer 返回新数组时变化；`dispatch` 引用稳定
- 只 dispatch 的组件（如新增表单）不随任务变化重渲染——今天要打日志验证
- 筛选条件**不要**放进这个 Context：它只影响列表展示，放本地即可

### 1.8 Vue 对照

| Vue | React | 关键差异 |
|---|---|---|
| Pinia `state` | `useReducer` state + Provider | React 手动管理不可变更新 |
| Pinia `getters`（缓存、依赖追踪） | render 时派生 / selector 纯函数 | 默认无缓存；需要缓存才上 `useMemo`（027） |
| Pinia `actions`（可异步） | reducer（同步纯函数）+ 事件处理 | 异步不进 reducer；将来放 Effect/事件 |
| `v-model="filter.keyword"` | 受控 `input` + `onChange` | 无双向绑定语法糖 |
| `storeToRefs` 字段级订阅 | Context value 整体比较 | 消费者按 Context 粒度重渲染，不按字段 |
| 多模块 store | 多 Context / 拆分 state-dispatch | 手动设计订阅粒度 |

### 1.9 常见坑

1. 过滤结果 / 计数放进 state → 与 tasks 不同步
2. 筛选条件放进全局 Context → 消费者无谓重渲染，且离开页面不重置
3. reducer 内生成 id、时间戳 → 不纯，StrictMode 放大
4. 更新任务时只改内层对象、外层数组引用不变 → `Object.is` 相等 → bailout，UI 不更新
5. `filter((t) => t.id)` 删除写反（应 `!==`）
6. 一个 Context 装 `{ tasks, dispatch }` → 只 dispatch 的组件跟着重渲染
7. 列表 key 用 index → 重排/删除时 DOM 状态错位（010）
8. 编辑草稿直接绑定任务对象 → 输入时全局状态已变，取消无法回滚；草稿应是本地副本
9. 空状态不区分「没有任务」和「筛选无结果」
