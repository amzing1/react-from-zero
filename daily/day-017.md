## 1. 核心概念（35 min）

### 1.1 Context 是什么

- Context 是**跨层传值**的通道，解决 prop drilling
- 它不是状态管理器：状态仍然放在某个组件（Provider 的拥有者）或外部 store
- 只有**调用了 `useContext` 的组件**才是消费者；中间组件不需要转发 props

```tsx
const ThemeContext = createContext<'light' | 'dark'>('light')

function App() {
  const [theme, setTheme] = useState<'light' | 'dark'>('light')
  return (
    <ThemeContext value={theme}>   {/* React 19 可直接用 Context 作为 Provider */}
      <Toolbar />
    </ThemeContext>
  )
}

function Toolbar() {
  return <ThemedButton />   // 中间组件不需要 theme prop
}

function ThemedButton() {
  const theme = useContext(ThemeContext)
  return <button className={theme}>...</button>
}
```

- `createContext(defaultValue)`：没有 Provider 时使用默认值
- `<Context.Provider value={...}>` 是传统写法；React 19 支持 `<Context value={...}>`
- 默认值适合“永远有合理默认”的场景；需要强制 Provider 时，默认值可以设为 `null` 并在消费处检查

### 1.2 什么时候消费者会重渲染

- Provider 的 `value` 变化（`Object.is` 比较）→ **所有消费者**重渲染
- Provider 自身因父级重渲染而重渲染，如果 `value` 是内联对象/数组/函数 → 新引用 → 所有消费者重渲染
- Context 不按字段追踪；只读 `theme` 的消费者，在 `user` 字段变化时也会重渲染（同一个 value 对象变了）
- `React.memo` **不能**阻止 context 更新：消费者订阅了 context，value 变了就会重渲染

```tsx
// ❌ 每次 Provider render 都是新对象
<AuthContext.Provider value={{ user, login, logout }}>

// ✅ 值稳定（或拆成多个 context）
const value = useMemo(() => ({ user, login, logout }), [user])
```

### 1.3 减少 Context 重渲染

1. **拆 Context**：ThemeContext / UserContext / DispatchContext 分开，消费者只订阅自己需要的
2. **稳定 value**：`useMemo` 包对象；函数用 `useCallback` 或直接把稳定的 dispatch 放进去
3. **state / dispatch 拆分**：`useReducer` 的 `dispatch` 引用稳定；只 dispatch 的组件放 DispatchContext，不随 state 变化重渲染
4. **组件组合**：把 `children` 作为 prop 传入，稳定子树；避免 Provider 重渲染时重建整棵树
5. **不要用 Context 传高频变化的值**：鼠标位置、输入框每个字符；用 selector 型 store 或局部状态

### 1.4 Context + useReducer

```tsx
const TaskStateContext = createContext<Task[]>([])
const TaskDispatchContext = createContext<Dispatch<Action>>(() => {})

function TaskProvider({ children }: { children: ReactNode }) {
  const [tasks, dispatch] = useReducer(taskReducer, [])
  return (
    <TaskStateContext value={tasks}>
      <TaskDispatchContext value={dispatch}>{children}</TaskDispatchContext>
    </TaskStateContext>
  )
}
```

- `dispatch` 稳定 → 只 dispatch 的组件不因 tasks 变化重渲染
- 读 tasks 的组件会重渲染
- 这是项目 B 的状态结构基础；比单个 `{ state, dispatch }` context 更细粒度

### 1.5 Context vs 状态库

| | Context | Redux / Zustand |
|---|---|---|
| 定位 | 传值通道 | 状态管理 + 订阅 |
| 更新粒度 | value 变 → 所有消费者 | selector 订阅，可细粒度 |
| 适用 | 低频：主题、语言、用户、dispatch | 高频/复杂：大表单、实时数据、跨模块 |
| 优化 | 拆分、memo value、组合 | 内置 selector/中间件 |

### 1.6 Vue 对照

| Vue | React |
|---|---|
| `provide(key, value)` | `createContext` + Provider |
| `inject(key, default)` | `useContext` + 默认值 |
| 提供 `ref` / `reactive` 才具备响应式 | Context value 按引用比较，变化即通知 |
| 依赖 Vue 的响应式追踪 | 无字段级追踪，value 变全体消费者重渲染 |
| `provide/inject` 也可传函数/对象 | Context 可传任意值（含 dispatch） |

Vue 的 `provide/inject` 本身只是注入；响应式来自被提供的 `ref/reactive`。React Context 的“响应式”来自 Provider value 的引用变化。

### 1.7 常见坑

1. 内联 `value={{ ... }}` → 每次 Provider render 全体消费者重渲染
2. 一个巨型 Context 装所有全局状态 → 任何字段变化全体重渲染
3. 以为 `React.memo` 能挡住 context 更新（不能）
4. 两层能解决的 prop drilling 也上 Context → 过度设计
5. Provider 缺失时静默使用默认值 → 用 `null` 默认值并在消费处检查
6. 用 Context 存高频变化的值 → 性能灾难
