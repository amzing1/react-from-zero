### 我的回答 / 讲评

**得分：3.8 / 5**

| 题 | 判定 | 得分 | 关键问题 |
|---|---|---|---|
| 1 Vite | ⚠️ | 0.5 | build 内核答对，dev 转换器答成 esbuild |
| 2 TS | ⚠️ | 0.8 | `strict` 子项只答出 3/8；两个独立选项答对 |
| 3 RSC | ✅ | 0.9 | 主体正确；「直接展示」表述不精确 |
| 4 快照 | ✅ | 1.0 | 完全正确 |
| 5 Vue 对照 | ⚠️ | 0.6 | Vue 侧正确；React「从根执行」不准确 |

**逐题纠正**

1. **Vite**：Vite 8 dev 转换器是 **Oxc**，build 内核是 **Rolldown**；esbuild 是 Vite 7 及以前。dev 不打包 = 浏览器原生 ESM + 按需转换；依赖预构建只处理第三方依赖。生产仍需打包：tree-shaking、代码分割、hash、压缩混淆。
2. **TS**：`strict` 是 8 项，口诀 `any / null / function / bind / property / this / always / catch`。`noUncheckedIndexedAccess` 是独立开关，原因是索引访问全变 `T | undefined`，迁移噪音大。`verbatimModuleSyntax` 强制 `import type`；`erasableSyntaxOnly` 禁止 enum/namespace 等生成运行时代码的语法。
3. **RSC**：服务端产出 Flight 序列化的 React 元素树，不是 HTML；客户端 React 仍要 reconcile。SSR 产出 HTML 并 hydrate。Server Component 永不 hydrate；只有 Client Component 会 hydrate。限制：不能用 state/Effect/DOM/browser API，props 必须可序列化。
4. **快照**：正确。补：开发模式 StrictMode 双调用 render，但 commit 一次。
5. **Vue/React**：Vue Proxy get 收集依赖（targetMap），set 触发对应 effect；React setState 在组件 fiber 上创建 update，调度从 root 开始，但只重渲染带更新的 fiber 及其子树，不是从根重新执行整棵树。核心差异是依赖追踪 vs 快照 + 组件级重渲染。

## 1. 核心概念（35 min）

### 1.1 复盘不是「再看一遍」：学习系统的四个杠杆

| 杠杆 | 做法 | 在本课程中的落点 |
|---|---|---|
| 检索练习 | 先闭卷回忆，再看答案 | 每日热身、闭卷自测、面试式追问 |
| 间隔复习 | 1/3/7/15 天回访 | `progress.md` 复习队列 |
| 交错练习 | 新旧主题混着考，而不是一次只练一个 | 热身题混合上次内容 + 到期复习项 |
| 错误反馈 | 把错题写成「错误理解 → 正确理解」 | `notes/mistakes.md` |

**为什么「看懂了」不等于「会」**：阅读带来的是熟悉感（fluency illusion），检索才暴露提取失败。React 的 API 数量不多，但心智模型要求高——**能复述**和**能预测代码行为**之间差距很大。

**Vue 对照**：Vue 的模板语法和响应式会自动「兜底」很多细节；React 把更多决策交给你（依赖数组、引用稳定、不可变更新），所以 React 学习更依赖主动检索和预测，而不是照抄模式。

### 1.3 弱项排序：用证据，不用感觉

**证据来源（按可信度排序）**

1. 闭卷自测的错题与「答不全」
2. 动手任务中真实卡住的点（报错、调试耗时）
3. Day 001 诊断的失分分布
4. `notes/mistakes.md` 的重复出现次数
5. 「感觉自己不会」——只能作为线索，不能作为结论

**排序公式（每项 1–5 分）**

```
优先级 = 影响面 × 出现频率 ÷ 补强成本
```

- **影响面**：后续多少课时依赖它（如渲染模型影响 007–030 全部）
- **出现频率**：最近 5 次练习中卡了几次
- **补强成本**：能否在 1–2 个课时内解决（成本低优先）

**Top 5 每条必须写清**：证据 → 正确理解 → 补强课时 → 验收方式。没有验收方式的补强项等于没有安排。

### 1.4 阶段 0 知识地图：一条主线，五个挂点

主线只有一个：**UI = f(state)**。

```
001 诊断：起点、目标、弱项
        │
002 渲染与状态：UI = f(state) → render/commit → 快照 → 批处理 → 不可变更新
        │
003 组件模型：组件即函数 → props/children → 组合 → Context → 挂载/卸载 → Hooks 规则
        │
004 React 19 全景：Actions / useOptimistic / use() / Activity / Compiler / RSC
        │
005 工程基线：Vite 8（Oxc dev / Rolldown build）+ TS 7 strict + alias + lint/format + DevTools
        │
006 学习系统：诊断 → 计划 → 执行 → 检索 → 错误日志 → 校准（闭环）
```

**把五课串起来的三个因果**

1. 因为 React 用**快照**而不是依赖追踪，所以更新必须**不可变**；因为不可变，才能用 `Object.is` 做 bailout，也才能让 Compiler 和并发渲染安全工作。
2. 因为组件是**函数**，所以 Hooks 必须按固定顺序调用；因为 render 必须**纯**，所以副作用要放进 Effect，StrictMode 才敢双调用。
3. 因为反馈要快，所以工程基线要**五层独立可执行**；因为学习要闭环，所以错题必须进队列并在 1/3/7/15 天回访。

### 1.6 Vue 对照：哪些经验可迁移，哪些必须重置

| 可迁移 | 必须重置 |
|---|---|
| 组件化、单向数据流、props 只读 | 响应式依赖追踪 → 快照对比 + 组件级重渲染 |
| 生命周期直觉（挂载/更新/卸载） | `watch` → `useEffect`（依赖数组、清理、闭包） |
| 工程化、构建、别名、环境变量 | `v-model` → 受控/非受控组件 |
| 性能意识、懒加载、代码分割 | `provide/inject` → Context（引用相等、全部消费者重渲染） |
| 组合式 API 的复用思维 | `keep-alive` → `<Activity>`（state 保留、Effect 清理） |

**学习策略**：每学一个 React 概念，做三步——① 写 React 版；② 写 Vue 对照；③ 写「为什么不同」。第三步才是真正的掌握。

**任务 D：阶段 0 验收表述（草稿）**

- **Vue**：Proxy get 收集依赖到模块级 targetMap（WeakMap），set 触发该属性对应的 dep 集合，只重跑读过该属性的 effect；ref 用 RefImpl 的 getter/setter + 自己的 dep。
- **React**：setState → dispatch 用 `Object.is` 比较新旧 state；不同则调度**拥有该 state 的组件实例**重新 render；render 返回新元素树，与当前 fiber 树 reconcile；commit 更新 DOM 并执行副作用。
- **为什么必须不可变**：`Object.is` bailout；快照稳定性（旧 render 闭包不被污染）；并发渲染保留多版本；Compiler 的 Rules of React 假设。
