## 0. 检索热身（10 min）

先闭卷回答（到期复习 + 错题重测）：

1. Vue 的 `emit`、默认插槽、具名插槽、作用域插槽、`provide/inject`，在 React 里分别怎么写？
2. `onClick={onSave("x")}` 错在哪？StrictMode 下会发生什么？
3. Context 的 `value={{ theme, toggleTheme }}` 为什么会让消费者额外重渲染？另外，为什么 Hooks 不能条件调用？
4. React 的 commit 阶段有哪些子阶段？`useLayoutEffect` / `useEffect` 分别何时执行？
5. `memo` 的浅比较与 bailout 条件是什么？「创建 element」和「执行组件函数」有什么区别？

### 我的回答 / 讲评

- **Q1 ✅**：emit → 回调 prop；默认插槽 → children；具名插槽 → ReactNode prop；作用域插槽 → 函数 prop；provide/inject → Context + useContext。
- **Q2 ✅**：render 期执行、点击无 handler、StrictMode 双调用；若回调里 setState 可能无限循环。
- **Q3 ⚠️**：Context 部分仍不完整——内联 `value={{...}}` 每次 Provider 渲染都是新对象，`Object.is` 失败，所有消费者重渲染（不论读哪个字段）。Hooks 链表/顺序部分正确。
- **Q4 ✅**：commit 子阶段为 before mutation → mutation → layout（useLayoutEffect）→ 绘制 → passive（useEffect）。
- **Q5 ⚠️**：`memo` 浅比较正确；但 element 创建只是生成普通对象，组件函数此时未执行，更不会“设置状态”。

## 1. 核心概念（35 min）

### 1.1 版本时间线（19.0 → 19.3）

| 版本 | 时间 | 主线 | 关键 API / 变化 | 典型场景 |
|---|---|---|---|---|
| 19.0 | 2024-12 | Actions + RSC 稳定 | `useActionState`、`useFormStatus`、`useOptimistic`、`use()`；ref as prop；`<Context>` 直接作 Provider；Server Components / Server Actions 稳定 | 表单提交、乐观更新、Next App Router |
| 19.1 | 2025-03 | 调试与 Suspense 改进 | Owner Stack / `captureOwnerStack()`（仅开发）、Parcel RSC、Suspense hydration 改进、`useId` 格式变更 | 定位「谁渲染了我」、框架集成 |
| 19.2 | 2025-10 | 可见性、Effect 事件、性能 | `<Activity>`、`useEffectEvent`、`cacheSignal`、Performance Tracks、部分预渲染（框架层） | 保留页面状态、拆分 Effect 中的非响应逻辑、性能分析 |
| 19.3 | 2026-09 | 视图过渡、Fragment ref、浏览器边界 | `<ViewTransition>` 稳定、Fragment refs 稳定、`react-dom` 的 `browser()`、Trusted Types、`onBrowserBailout` | 过渡动画、无包裹节点操作、明确 CSR-only 子树 |

> 版本核对：本地 `react@19.3.1` / `react-dom@19.3.1`；实际导出包含 `Activity`、`ViewTransition`、`cache`、`cacheSignal`、`useEffectEvent`、`useActionState`、`useOptimistic`、`use`，以及 `react-dom` 的 `browser`。

### 1.2 三层心智模型

| 层 | 内容 | 使用原则 |
|---|---|---|
| 日常 API | 组件、props、state、Effect、Context、列表/表单、事件 | 先把这一层写对；大多数业务不需要并发 API |
| 并发与新范式 | Transition、`useDeferredValue`、Suspense、Actions、`useOptimistic`、`use()`、`Activity`、`ViewTransition` | 解决「更新优先级 / 异步边界 / 交互体验」，不是状态设计的替代品 |
| 框架与底层 | RSC、Server Actions、Compiler、Fiber/Scheduler、Next.js | 框架层能力，先理解边界再用；原理阶段再拆实现 |

**判断顺序**：先问「状态设计对不对」→ 再问「是否需要异步边界/优先级」→ 最后才考虑框架或编译器。

### 1.3 新范式速览

- **Actions**：把「异步 mutation + pending + 错误 + 表单重置」交给 React。`useActionState` 管状态，`useFormStatus` 读父表单提交状态，`useOptimistic` 做乐观更新。
- **`use()`**：在 render 中读 Promise/Context，可以条件调用；Promise 必须在 render 外创建或缓存，否则 Suspense 会反复触发。
- **`<Activity>`**：`mode="hidden"` 时隐藏子树、卸载 Effect、保留 state；`visible` 时恢复。适合预渲染下一页、保留表单/滚动状态。
- **`useEffectEvent`**：把 Effect 中的「非响应式事件逻辑」抽出来，始终读最新 props/state，且不放进依赖数组。
- **`<ViewTransition>`**：基于浏览器 View Transition API，在 transition / Suspense 揭示时做进出场、共享元素动画；`addTransitionType` 标记过渡原因。
- **Fragment refs**：ref 直接挂到 `<Fragment>`，拿到 `FragmentInstance`，不用额外包 `<div>`。
- **`browser()`**：`use(browser())` 让子树在服务端挂起、客户端立即返回，用来表达「这段只能在浏览器渲染」。

### 1.4 React Compiler 的定位

- 构建期自动 memoization，1.0 于 2025-10 稳定；Next.js 16 已稳定支持，Vite 等也可接入；通过 runtime 兼容 React 17+。
- 它优化的是「重复计算 / 引用稳定性」，**不改变**不可变更新、纯度、Hooks 规则。
- 仍可能需要手写 `useMemo` / `useCallback`：编译器未覆盖的代码（非组件/第三方边界）、编译器 bailout 的场景、需要显式语义或与外部库对接时。
- 面试口径：Compiler 减少「为了性能而写」的 memo，但不替代性能分析与架构设计。

### 1.5 RSC 与 Next.js 16 的边界

- **RSC 不是 SSR 的替代品**：SSR 负责首屏 HTML；RSC 是一种组件模型，服务端组件不进入客户端 bundle，通过 Flight 协议传输。
- `'use client'` 标记客户端边界；Server Component 不能使用状态/Effect/DOM API；props 必须可序列化。
- Server Actions 用 `'use server'`，从客户端调用服务端函数；注意鉴权、输入校验、幂等与安全。
- Next.js 16（2025-10）主线：App Router、Turbopack 默认、Cache Components（`'use cache'`）、React Compiler 稳定支持、`proxy.ts` 替代 `middleware.ts`、异步 `params/searchParams`。

### 1.6 生态地图与选型

| 领域 | 主流选择 | 适用场景 / 边界 |
|---|---|---|
| 组件内状态 | `useState` / `useReducer` | 默认起点 |
| 跨层共享（低频） | Context | 主题、用户、i18n；高频变化要拆分/下移 |
| 全局客户端状态 | Zustand / Redux Toolkit / Jotai / XState | Zustand 轻量；RTK 适合大团队与严格调试；Jotai 原子化；XState 状态机 |
| 服务端状态 | TanStack Query / SWR | 缓存、重试、失效、Mutation、乐观更新；不要塞进全局 store |
| 路由 | React Router v7 / TanStack Router / Next App Router | 数据路由、类型安全、全栈/RSC 分别对应 |
| 表单 | react-hook-form + zod | 复杂表单/校验；简单表单可用 React 19 Actions |
| 样式 | Tailwind / CSS Modules / CSS-in-JS / Radix + shadcn + cva | 团队规范优先；scoped 不是内置能力 |
| 测试 | Vitest + RTL + MSW；Playwright | 单元/集成/E2E 分层 |
| 构建/元框架 | Vite / Next.js（Turbopack）/ Rspack / Expo | SPA、全栈、RN 各自不同 |

**选型原则**：先用内置能力；出现明确的缓存/失效需求再加服务端状态库；出现跨树共享再加客户端 store；需要 SSR/RSC/全栈再上元框架。

### 我的实现 / 遇到的问题

**版本验证（2026-11-18）**

- `react@19.3.1` / `react-dom@19.3.1`
- `react` 实际导出包含：`Activity`、`ViewTransition`、`cache`、`cacheSignal`、`use`、`useActionState`、`useOptimistic`、`useEffectEvent`
- `react-dom` 实际导出包含：`browser`、`preload`、`preinit`、`flushSync`
- 与预期一致；`browser()` 已在 19.3 提供，但官方文档仍标注 Canary 渠道，生产使用需核对

**Activity 实验**

```tsx
const [mode, setMode] = useState<"hidden" | "visible">("visible");

<Activity mode={mode}>
  <Counter />
</Activity>
```

观察结果：

1. 切到 `hidden` 再切回 `visible`，Counter 的计数**保留** → Activity 不卸载组件，state 保留
2. `hidden` 时 Effect 执行 cleanup，切回 `visible` 时重新 setup
3. 对比 `{visible && <Counter />}`：条件渲染会真正卸载，**state 丢失**；Activity 不会

结论：Activity 介于 `v-if`（state/Effect 全丢）与 `v-show`（state/Effect 全留）之间——**state 保留、Effect 卸载、更新延后**。

## 3. 闭卷自测（10 min）

**得分：7 / 10**

**Q1｜版本主线** ✅
19.0 Actions/`useActionState`、19.2 Activity、19.3 ViewTransition，主线都正确。

**Q2｜Actions** ⚠️
- `useActionState`：管理异步 action 的返回值/错误 + pending ✅
- `useFormStatus`：读取父级 `<form>` 的提交状态（pending/data/method/action），必须放在 form 的子组件里；不是“管理表单内部状态”
- `useOptimistic`：action 期间先展示预期结果，结束/失败后回滚（点赞、评论、购物车）
- Actions 省掉：loading、error、表单重置、重复提交保护、渐进增强

**Q3｜Activity** ✅
state 保留、Effect cleanup；`v-if` 全丢，`v-show` 全留；Activity 介于两者之间（更新还会延后）。

**Q4｜Compiler** ✅
大多数手写 memo 可去掉，但以下仍需：编译器 bailout（违反 Rules of React）、未覆盖的代码（工具函数/`node_modules`/排除文件）、第三方库引用稳定性契约、需要显式性能控制。

**Q5｜RSC** ⚠️
- SSR：服务端渲染 HTML 首屏，客户端 hydration
- RSC：Server Component 在服务端执行，输出 Flight 组件树，**不进入客户端 bundle、不 hydrate**；只有 Client Component 会 hydrate；两者可组合（Next.js）
- Server Component 限制：不能用 state/Effect/DOM/browser API；props 可序列化；不能导入客户端专用库；`'use client'` / `'use server'` 标边界
